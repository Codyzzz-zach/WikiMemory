## 结论

本轮主结论是：**当前 P/E-min 没有优于直接 Markdown 检索 B，主要失败点是知识检索的种子召回，而不是已召回知识的回答质量。**

因此按照预先锁定的决策规则：

1. 暂停扩展到 20 篇材料。
2. 暂停继续增加 WikiModule。
3. 下一施工目标改为 Claim seed retrieval / Context Pack 召回修复，并用独立 Dev 题回归。
4. 暂不直接删除 Graph：Relation 激活子集上 P 与 B 基本持平，H3 小样本甚至略高；应先把“检索不到种子”与“Graph 本身无价值”分开。

## WikiModule 结果

## Answerability 与安全性

唯一 INSUFFICIENT 题中：

- B 使用不相关材料补出 Lebesgue/Riemann 对比，触发硬失败。
- P/E-min 因上下文明确不足而正确拒答，均为 8/8。

这是 P/E-min 当前最清晰的产品价值证据：**当知识系统明确知道没有证据时，它比原文词法检索更不容易编造。**

代价是召回失败时同一机制会错误拒答。下一阶段目标不是放松证据门禁，而是提高证据召回。

## Source-risk 题

`PILOT-C01` 三组均失败。该题要求识别第 05 章中 `L²→L¹` 图示遗漏有限测度条件：

该题说明 source-risk/provenance 信息尚未进入可消费 Context Pack。它不应与普通问答题混为同一种失败。

## 评分器偏差复核

AI judge 与回答模型相同，因此只能作为一致性评分器，不是独立人工裁判。发现两类偏差：

1. Judge 对可读但非法 JSON 的答案仍可能给满分，所以格式失败单独计数。
2. Judge 有时因 P/E-min 使用 `claim:` 或 `wiki://` 标识而扣 evidenceGrounding，尽管这些标识确实存在于当次上下文。确定性复核结果：所有可解析答案中的引用均能在各自请求上下文中找到——B 41/41、P 40/40、E-min 40/40。

其中 E-min 有 3 个答案额外引用 Wiki 地址，但同时也引用了 Claim；Answer system 要求关键结论落到 SOURCE/EVIDENCE/CLAIM，因此这些 Wiki 引用不能单独充当证据，但也不应让其余可解析 Claim 引用失效。

由于这些偏差主要影响 evidenceGrounding 维度，不足以解释 P/E-min 在 6 道可回答题上的错误拒答，主结论保持不变。

## 下一阶段可证伪目标

下一阶段不再增加材料，目标改为：

> 在不放松 evidence fail-closed 的前提下，把五篇冻结语料上普通 answerable 题的 requiredSources 召回从 53.9% 提高到至少 85%，并把低上下文错误拒答从 6/14 降到不超过 1/14。

建议施工顺序：

1. 为 Claim statement 建立适合中文/数学符号的确定性 seed retrieval，而不是依赖当前全有或全无的匹配。
2. 先召回 Claim/Evidence，再沿已审计 Relation 扩展；Graph 不应承担“从零找到第一个节点”的职责。
3. 当 Claim seed 为空时，增加受预算约束的 canonical Claim fallback，不直接退化成 143-token 的空 Context Pack。
4. 将 source-risk / known-gap 作为独立可召回对象，不能只存在于审计记录里。
5. 用独立 Dev 题验证召回修复，再对本冻结 Pilot 只做一次复跑，避免围绕 16 题逐题打补丁。

若完成上述召回修复后，Relation-active 与全量结果仍不优于 B，再进入“收缩 Graph/Compiler 复杂度”的架构决策。
