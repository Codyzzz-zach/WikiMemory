01 / Executive Verdict

工程地基与局部索引已建立；现在要从局部算法调参转向规模、时间和最小产品飞轮

旧版 v0.9 判断 Relation 发布、原子快照、跨材料扫描和演化链路尚未闭环；这些结论已经过期。当前系统已经具备不可变证据、有界编译、Claim/Relation 双门禁、物理隔离、两阶段原子发布、知识快照、跨材料扫描和受审批的纠正/冲突事务。新的主要矛盾不再是“能否安全写入”，而是“严格投影是否损失了太多真实语义，以及这些结构是否真的让 Agent 长期变好”。

KEEP

保留安全知识状态内核

Evidence、Canonical/Quarantine、四状态轴、双门禁、原子发布、版本和回滚是错误复利场景下的必要基础，不能因为小规模原文检索暂时领先就拆掉。

SHIFT

停止继续围绕通过率优化

G0 已补齐过程留痕与闭包，G3-A 已完成局部索引；不再无限优化已失败的 R1。G3-B3 已结清成本账并冻结结构化 Claim transport 候选；当前跑一次 S50/S200/S1000 与 T0→Tn 的 G3-C，随后实现最小 Wiki+Correction 飞轮。现有 A/B/C 均为 Dev/Regression。

当前最危险的自我欺骗：把“原文仍在磁盘”当成“Agent 没有损失知识”，或把“错误边被隔离”当成“Graph 已经高质量”。原始证据可恢复只证明没有不可逆删除；默认消费投影是否保留了任务所需事实、条件、语境和关系，必须另行测量。
02 / First Principles

知识编译不是提取比赛，而是一个受约束的有损变换

Claim / Relation / Wiki"] K --> P["任务投影 P(K,q)

任何压缩都会丢信息。问题不是“能否零损失”，而是：是否丢掉了对未来任务重要的信息；是否引入了原文没有的内容；丢失后能否发现并回退到原文；新证据进入后是否能局部修正而不污染无关知识。

不变量必须保证对应指标不能用什么替代
真实性每个可消费断言和强关系都有可解析来源错误引用率、无证据发布率、审计精度节点数量、模型置信度
语义保留事实、条件、例外、指代、表格和推导链不被原子化破坏Source→Claim 召回、条件保真、Quarantine 假阴性eligible block 100% 命中
任务效用有限 token 下提供更相关、更完整的任务上下文同实际 token 的回答质量、hard failure、延迟Context Pack 看起来结构化
可演化纠正、冲突和新知识改变后续行为，同时不伤害无关知识复发率、影响发现率、无关回归、局部更新范围生成新版本或 Git commit
可恢复失败不破坏 last healthy；能回到原文和历史状态原子性、回滚、悬空引用、恢复时间“文件还在”
架构判断原则：安全门禁与 Typed Graph 的长期治理/候选导航职责有第一性原理和 CodeGraph 实现依据，作为架构公理保留；具体 Relation 类型、边权、ranking、可见路径、Wiki 结构和 Board 模式仍必须通过过程信号、规模/时间实验与 Held-out 优化，不能把“Graph 必要”误写成“任意 Graph 实现都正确”。
03 / LiteWikiagent Heritage

LiteWikiagent 是经验库，不是要复制的旧架构

旧项目真实解决过“如何让 Agent 阅读和探索知识”的问题，也真实暴露了“生成式 Wiki 如何把推断伪装成知识”的问题。后续施工必须同时继承它的产品洞察和吸收它的工程教训。

应继承

面向 Agent 的语义组织

  • 围绕问题与概念组织可读模块；
  • 显式表达 Interpretation、Use For、Limits；
  • concept/method/case/question/insight/counter 等不同知识角色；
  • ask/trace/expand/compare/challenge/inspire 等任务视图；
  • 文件、图和向量的混合检索经验；
  • Loader、daemon 和持续摄入的产品体验。
必须拒绝

写入先于可信边界

  • 无证据时回退到虚假的固定引用；
  • 生成 Interpretation 后再尝试审计；
  • 审计异常静默、文件仍已写入；
  • 旧节点先删除、新快照未原子完成；
  • 关系只凭同主题或模型置信度发布；
  • 把人类可读页面直接当作知识权威。
应重建

在 Canonical 之上的 Wiki

  • WikiModule 只能引用 Canonical Claim；
  • 解释文本中的每个断言可追溯 Claim；
  • 稳定地址与内容版本分离；
  • Claim 失效时模块自动失效或重建；
  • Board 模式成为同一知识状态的运行时视图；
  • 探索性推断必须与来源事实分层展示。
旧经验当前系统下一代正确组合
Wiki 页面连贯、适合阅读，但容易把推断写成事实Claim 可审计，但阅读时碎片化Canonical Claim 是权威；WikiModule 是可重建的语义视图
六种 Board 提供丰富任务脚手架单一 Context Pack 更简单可控先冻结统一 Pack 合同，再把 Board 作为可消融的选择策略
混合检索召回强，但失败可静默降级词法 Seed 可解释，但召回仍有限统一候选日志下比较 lexical/BM25/vector/graph，不把任一路写死
PDF/TeX 与 watcher 体验较完整只实现 Markdown，Loader 已解耦产品价值成立后复用旧 Loader 经验接入，不把格式逻辑塞进 Compiler
历史经验使用规则：旧项目可以提供需求、反例、测试案例和实现思路；不能直接复制其未经当前证据合同验证的节点、关系、审计分数或发布逻辑。

历史工作包 B · G1 底座与首个 G2 R1（已完成并判 Rework）

目的：验证 Graph 候选导航、排序和可见门禁；当前产品口径已修正为按任务条件触发，而不是每题默认参与。

  1. 用混合 Seed 找入口；只在当前审计版本可消费的局部图上做有界扩展。
  2. 结构排序参考 CodeGraph 的“文本入口 + 局部候选图 + RWR/PageRank + relevance gate”，但加入 WGEMemory 特有的 provenance、condition 和 relation audit 权重。
  3. 多锚点且存在可信连接链时才展示路径；弱主题关联只可影响排序，不可冒充推理证据。
  4. Graph 内容必须挤占同一可见预算，而非额外叠加；边际收益不足时收窄可见路径并回到 ranking/gate 诊断，不取消长期 Graph 架构。
  5. 当前每题全库读取/构图只能作为开发实现；规模扩大前改为持久索引和查询时局部读取。
G1 当前裁决：Relation audit v2.3 在 35 条 AI post-hoc 组合代理集上得到强边 precision=1.00、recall=0.769；这不是人工 Gold。16 题隔离准备中，单锚解释扩展触发 2 题，P-graph 比 P-seed 平均多 810 Context tokens，而两组模型代理评分均为 8/8、0 硬失败，因此该策略被否决。当前实现收紧为：解释型边必须连接两个独立 Seed；安全型边可从一个 Seed 扩展。修正后 16/16 P-seed 与 P-graph Context hash 相同。权威证明为 experiments/goal1/goal1-proof-v1.json，状态 PASS_ENGINEERING_GATE_NO_PRODUCT_GAIN。
不得误读：G1 证明“系统能识别并撤销无收益的 Graph 扩展”，没有证明“Graph 已提高回答质量”。G2 的目标是让可信结构参与候选排序或替换低价值 Seed；若仍只做追加，任何正分都可能被额外 token 混淆。

持续工作包 C · 用短 Loop 驱动修改，再进入新盲集

目的：既不继续逐篇盲目重编，也不在不可解释的输入上直接追逐最终产品分数。

  1. Freeze：冻结代码、配置、模型、temperature、知识快照和题目 hash。
  2. Observe：先跑 4–8 题 Micro，读取过程 trace 与结果，不先全量。
  3. Diagnose：把失败归因到编译漏失、Seed 召回、Graph 排序、预算裁剪、答案或 Judge。
  4. Change：每轮只修一个可证伪假设，不增加领域、题号或 Gold 特判。
  5. Evaluate：通过 Micro 后跑扩展 Dev；比较 B / R0 / R1 的配对质量、hard failure、精确 token、延迟与过程指标。
  6. Archive：封存首轮与 post-hoc 输出；架构大改可重编并全量重跑全部历史资产作为 Dev/Regression，但不得覆盖旧结果或恢复 Blind 身份；G3-C 与最小飞轮候选冻结后再新建真正未揭示的 Held-out。
Reasonix 权限结论：过去的调用有提示词级角色分工和全局 sandbox，但没有证明净化 worktree、路径 allowlist、候选 hash 后 Gold 解封和 Evaluator 只读。完成项目级物理隔离前，Reasonix 只能执行 Dev/Post-hoc；新的 Blind 必须采用 Worker / Evaluator / Codex+Human Adjudicator 三方硬分离。

完整执行合同见 WGEMemory4LLM-Iteration-Operating-Plan.md。本文负责审计方向，Operating Plan 负责日常迭代。

09 / Definition of Usable

产品到什么程度才可以称为“可用”

“可用”不是一个布尔词。必须区分工程可用、受控 Pilot 可用和真实产品可用。当前系统处于 L1 与 L2 之间：安全内核可用，但 Agent 产品尚不可用。

级别定义硬门槛当前状态
L1 · 工程内核可用开发者可以安全摄入、编译、隔离、发布、查询和回滚悬空引用=0；失败保留 last healthy；状态和 run 可审计；默认消费 fail-closed基本达到
L2 · 受控知识库可用在多个领域中，系统能保留事实与条件，并生成可更新 Wiki独立 Gold 上 Claim precision ≥95%、事实 recall ≥90%、条件保真 ≥90%；强 Relation precision ≥90%、recall ≥70%；Quarantine 假阴性有界；Wiki 更新回归通过未达到
L3 · Agent Pilot 可用在相同实际 token 和独立 Held-out 上，编译知识提供可重复的质量或成本优势质量不劣于强文件检索超过 2%；hard failure 不增加；在不降质时上下文成本下降 ≥40%，或同成本回答质量显著提升；纠正后复发率 ≤5%未达到
L4 · 产品可用真实用户/Agent 在持续使用中明显变得更省解释、更少复发、更完整至少 30 天、5+领域、100+真实任务、2+纠正周期；重复解释下降 ≥30%；旧错复发 ≤5%；跨材料完整性优于基线；可恢复且维护成本可接受尚未验证
这些阈值是 v3.0 保留的产品验收基线，不是当前成绩。它们可以在首次预注册前基于成本和样本量调整；一旦 Held-out 开始运行，不能根据结果下调门槛。L2 是内部知识库可试用线，L3 是小范围 Agent Pilot 线，只有 L4 才能对外称“持续自进化知识产品可用”。

立即停止或收缩的条件

  • WikiModule 完成后仍无法在同预算下接近强文件检索，且没有显著 token/延迟收益；
  • 严格门禁导致事实或关系 recall 长期低于门槛，必须靠人工逐条补救；
  • 纠正后旧错误仍复发，或无关知识随着演化持续退化；
  • Graph 可见内容持续引入 hard failure——关闭或收窄可见路径；结构排序若暂时无边际收益，回到边质量、规模、ranking 与 gate 诊断。Typed Graph 的治理和候选导航目标不因单轮问答消融而删除；
  • 文件夹 + Agent 在相同预算和长期任务上稳定达到同等效果——此时产品应收缩为轻量文件组织或 Agent Skill。
10 / Final Alignment Statement

后续施工与审查的统一口径

WGEMemory4LLM 的最终产品不是一个更严格的 Claim 抽取器，也不是默认把 Graph 展开到 Prompt 的浏览器。它应当把原始材料安全地编译为可演化知识状态，再用 Graph 治理和选择、用 Wiki 组织语义、用受预算约束的 Context Pack 改善同一个 Agent 的后续行为。Evidence 决定它可信，Graph 决定知识如何关联与被选中，Wiki 决定它如何被理解，Evolution 决定它会成长，真实长期结果决定它是否值得存在。
  1. 从 LiteWikiagent 学产品表达，不能继承其 fail-open 权威模型。
  2. 当前安全内核、Trace、闭包和持久索引继续保留；Graph 在线候选导航按任务条件触发，失败 R1 不进入默认路径。
  3. 现有测试集只做回归；主结论必须来自独立 Held-out 与真实长期使用。
  4. 下一施工依赖固定为：当前一次 G3-C transport/规模/时间 → 最小 Wiki+Correction 飞轮 → 新硬隔离 Held-out → 真实 Pilot；G3-B3 已封存，不回到已揭示 50 题调参，也不是机械线性 G0→G7。
  5. 达到 L3 才允许小范围试用，达到 L4 才能称为产品可用。
