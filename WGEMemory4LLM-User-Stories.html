WGEMemory4LLM · User Stories v1.6

从“一篇新文章”到“一个真正进步的 Agent”

这份文档不是描述后台能生成多少文件，而是定义用户在长期学习中应该感受到什么：不维护 Wiki、不重复解释、不被陈旧结论拖回原点，同时能追问“为什么”“从哪里来”“这次和上次哪里不同”。

总用户故事：作为持续学习科技、AI、金融、历史、健康、人文等混合知识的单用户，我希望把主动选择的文章、讨论记录、项目材料与纠正交给通用 Agent 后，它能围绕长期问题自动形成并维护可追溯的加权证据拓扑；当我提出新问题时，它能复用跨材料关系、说明当前领先分支、冲突、条件与变化，并随新材料持续修订判断，而不要求我人工维护知识库。

01 / Actors

谁在使用，谁在消费，谁在后台负责

Primary beneficiary

多领域知识学习者

持续阅读科技、AI、金融、历史、数学、人文、心理、健康、生物与设计等混合材料，关心形成全局认识、发现冲突、复用历史学习，而不是管理知识库结构。

成功感受：Agent 记得已经讨论和纠正过什么，能用新材料改进旧认识。

Primary consumer

通用 Agent

接收任务化 Context Pack，并据此回答、比较、解释或给出建议。它不需要理解底层文件布局，但必须遵守证据、状态和风险标记。

成功感受：在有限上下文内拿到完整且任务相关的知识。

Internal responsibilities

知识系统角色

Ingestor 负责来源；Compiler/Librarian 维护知识状态；Linter 在消费前守门并定期修缮。这些是系统职责，不是三个人工岗位。

成功感受：自动运行、可解释失败、可恢复。

flowchart LR U["用户：提问 学习 纠正"] --> A["通用 Agent：执行任务"] A --> M["WGEMemory：提供 Context Pack"] S["用户选择的材料与反馈"] --> I["Ingestor"] I --> C["Compiler Librarian"] C --> L["Linter"] L --> M M --> A
体验边界：“AI 自治写入”不意味着用户永远不能查看底层。用户可以追溯、查看 diff 和回滚，但这些是信任与故障工具，不应成为正常使用前提。

03 / Canonical Journey

主用户故事：一篇新文章如何改变后续学习

示例情境：用户长期学习 Agent Memory / Context Engineering。系统已有多篇关于 RAG、长期记忆、知识图和 Context Pack 的材料。用户加入一篇新文章，其中对“何时应该提前编译关系”提出了不同结论。

sequenceDiagram participant U as 用户 participant A as 通用 Agent participant M as WGEMemory participant C as Compiler participant L as Linter U->>A: 把这篇新文章加入我的学习材料 A->>M: 提交材料与学习域 M->>C: 标准化来源并比对当前状态 C->>C: 提取 Claim 关系与 Wiki diff C->>L: 候选知识变更 L-->>M: 通过项 争议项 隔离项 M-->>A: 影响摘要与可用状态 A-->>U: 已更新哪些主题 发现什么冲突 U->>A: 现在 Graph 应该进入在线检索吗 A->>M: 请求任务子图与证据 M-->>A: Context Pack 含支持 反对 条件与来源 A-->>U: 给出条件化判断并解释新旧变化

用户可见的八幕

  1. 投递：用户把文章交给 Agent，不选择 chunk、不标注概念、不编辑 Wiki。
  2. 确认：Agent 告知材料已接收、是否重复、是否可解析；不把“开始处理”说成“知识已更新”。
  3. 影响：编译完成后返回影响摘要：新增哪些认识、修改哪些主题、发现哪些冲突、哪些内容仍被隔离。
  4. 提问：用户围绕长期问题提问；Agent 不读取整个 Wiki，而请求任务化 Context Pack。
  5. 回答：答案整合多份来源，显式说明支持、冲突、适用条件与仍未知部分。
  6. 追溯：用户问“为什么”，Agent 能展示关键 Claim → Relation → SourceSpan 路径，而非只给一串文件名。
  7. 纠正：用户指出误解，或明确选择并提交一份记录真实任务结果的材料；系统把该材料作为候选新证据处理，触发影响分析与回归。运行事件本身不会自动进入知识。
  8. 复利：几天后类似问题再次出现，Agent 使用修正后的状态，不要求用户重复解释，也不复发旧错误。
真正的 done：故事不是在“Wiki 文件生成”时结束，而是在新材料或纠正已经改变后续 Context Pack 和 Agent 行为时结束。
04 / Detailed Stories

P0 与 P1 用户故事、验收标准和信息流

P0用户证据不可变

US-01 · 投递材料，不做人工知识整理

作为知识学习者，我希望先把 Markdown 正文交给 Agent，从而让系统自行吸收，而无需选择切片、标签、页面或关系；未来增加 PDF、网页或 TeX 时不改变知识编译合同。

验收：当前 Markdown Loader 返回稳定 Source ID、内容哈希、解析状态和是否重复；相同内容重复投递不生成重复知识；解析失败只进入失败队列，不生成伪 Claim。格式扩展必须通过统一 DocumentLoader → LoadedDocument → Source/Span 边界，不能把格式逻辑塞进 Compiler。
Given 同一篇文章已经成功摄入 When 用户再次提交相同内容但文件名不同 Then 系统识别内容哈希重复，不重复创建 Source、Claim、Relation 或 WikiModule And 向 Agent 返回“已存在”的可解释结果
P0Agent演化优先

US-02 · 自动把新材料编译为知识状态 diff

作为通用 Agent，我希望知道新材料对当前知识造成了什么变化，从而向用户说明“学到了什么”，而不是只说“已生成摘要”。

验收：输出新增/修改/争议/取代/限域/未决/隔离的 Claim、Relation 与 WikiModule 清单；新材料优先更新稳定问题模块；每个 diff 可回到 SourceSpan，并解释分支权重、可见性或适用范围为什么改变。
flowchart LR S["新 Source"] --> C["候选 Claim"] C --> M["Concept 对齐"] M --> R["Relation 候选"] R --> D["Wiki Graph diff"] D --> O["影响摘要"]
P0系统消费前门禁v1.1 扩展

US-03 · 全部自动保存，但失败内容不污染默认消费链

作为用户，我希望AI 可以完全自治写入，同时错误或证据不足内容不会立即影响后续回答，从而不承担逐条审批负担。

验收：候选自动保存；结构、引用或支持度失败时进入 Quarantine；Quarantine 必须物理隔离（独立存储，默认读取 API 看不到）——不仅是状态标记；门禁覆盖 Claim 和 Relation（端点必须 Canonical）；修复后可重新候选。
Given 编译器生成一条没有可定位原文的关系 When 写入时 Lint 运行 Then 关系被保存到 Quarantine 并附失败原因 And 它不能改变默认检索排序或出现在 Canonical Context Pack 中 And v1.1：它被写入 quarantine/relations.jsonl 独立目录，readAllRelations 默认不读取它
P0用户 + Agent任务化上下文

US-04 · 用跨材料全局视野回答真实学习问题

作为知识学习者，我希望问“Graph 与 RAG 的边界是什么”时，Agent 能基于多篇材料组织给定版本、范围与任务下的当前领先认识，从而得到一份有关联、有冲突、有条件、保留不确定性的答案，而不是若干独立摘要。

验收：Context Pack 包含任务地图、关键 WikiModule、关系路径、必要原文、冲突和条件；回答不要求用户再次说明已知背景；上下文不超过约定预算。
flowchart TD Q["用户任务"] --> I["意图与范围"] I --> M["全局知识地图"] M --> G["任务子图"] G --> W["Wiki 语义"] W --> E["关键原文证据"] E --> P["Context Pack"] P --> A["Agent 回答"]
P0Agent类型化关系

US-05 · 沿可解释路径完成多跳连接

作为通用 Agent，我希望从任务种子概念沿 REQUIRES、DERIVED_FROM、SUPPORTS 等关系找到跨文档依赖，从而减少每次从零搜索并补全隐含中间步骤。

验收：路径中的每条边有类型、方向、条件与证据；RELATED_TO 只能引导进一步检索；超过深度/预算时返回截断说明，不伪装为完整路径。
Given 任务需要 A → B → C → D 的三跳知识路径 When Runtime 选择任务子图 Then Context Pack 保留必要中间 Claim 与边类型 And 每条用于答案的边都有来源或被明确标记为推断
P0用户可追溯

US-06 · 从回答回到原文，而不是相信系统口吻

作为用户，我希望追问某个关键判断的来源，从而能核对作者原话、适用范围和系统综合过程。

验收：关键结论提供 Claim → Relation/WikiModule → SourceSpan 路径；定位到页码、段落或行；区分原文明确陈述与 AI 推断；引用失效触发错误而非返回近似来源。
P0用户 + 系统诚实冲突

US-07 · 新文章与旧认识冲突时，不静默选边

作为用户，我希望新证据出现冲突时系统保留双方及适用条件，从而理解分歧来自定义、时间、场景还是事实错误。

验收：创建 CONTRADICTS 或条件化关系；相关 WikiModule 保留双方证据并标出争议；允许依据权威、当前性、适用性和关系支持给分支不同优先级，但必须解释依据，不能因展示领先分支而删除另一方；若没有真实 counter，诚实返回“未发现相关反证”。
flowchart TD N["新 Claim"] --> X{"与旧 Claim 冲突吗"} X -->|"否"| S["支持或补充"] X -->|"是"| C["记录双方证据"] C --> D{"条件能消解吗"} D -->|"能"| K["加条件并分叉适用范围"] D -->|"不能"| F["保留 Conflict"] K --> W["更新 Wiki 与后续回答"] F --> W
P0用户纠正进入闭环v1.1 双通道

US-08 · 用户纠正会改变后续行为，而不是停在当前对话

作为用户，我希望指出”这个结论不对，因为忽略了有限测度条件”后，系统能修正长期状态，从而以后不再重复同一错误。

验收：纠正分双通道处理。事实通道：旧 Claim → DISPUTED；新 Claim → HUMAN_ASSERTED + UNRESOLVED + CANDIDATE（不自动证明为真）；建 CONTRADICTS；获得来源后才 SUPPORTED。决策/偏好通道：绑定 AssertedRecord + 作用域校验后可直接 SUPPORTED + CANONICAL。分三阶段实现（2a-1 Claim 状态闭环 → 2a-2 WikiModule → 2b 派生层闭环）。只有完成派生层重编译及“不复发”回归后才算产品闭环闭合。
Given Canonical 中存在无条件的 “L² 属于 L¹” When 用户补充“仅在有限测度空间等条件下成立” Then 旧 Claim 进入 DISPUTED，停止无条件消费 And 新 Claim 为 HUMAN_ASSERTED + UNRESOLVED + CANDIDATE（不自动成真） And 建立 CONTRADICTS 边 And Context Pack 表达“原结论受到挑战，目前待核实”（而非自动相信用户说法） And v1.1：纠正产生 KnowledgeStateChanged 事件，驱动后续 Wiki 重编译
v1.1 非对称原则：用户的纠正足以让系统立即停止无条件相信旧结论，但不足以自动证明用户的新结论为真。项目决策/偏好例外——绑定 AssertedRecord + 作用域校验后可直接生效。
P0Agent时态与取代

US-09 · 区分“曾经正确”和“当前有效”

作为通用 Agent，我希望知道系统在某个知识版本中记录了什么、某个分支为什么被降权或取代，以及这些判断适用于什么范围，从而回答历史知识快照或旧版本问题时保留旧对象，回答当前问题时使用可解释的领先分支而不是机械采用最新 ACTIVE。

验收：完整支持 knowledgeVersion / recordedAt / knowledgeAsOf；明确来源版本和受审计 SUPERSEDES 是当前/历史选择的重要依据，但还必须保留权威、条件、适用范围和任务语境；新材料获得重新检查的当前性先验，不自动成为真理；旧对象不删除。validFrom/validTo 可保存来源中的时间条件，但 MVP 不宣称已经支持任意现实世界 validAt 区间推理。
P1用户变化可解释

US-10 · 看见“这次为什么和上次答得不同”

作为用户，我希望Agent 能解释答案变化来自哪些新材料、纠正或关系变化，从而判断这是知识进化还是模型随机波动。

验收：提供知识状态版本、关键 diff、受影响路径和回答使用的新证据；纯模型措辞差异不能被描述为知识进化。
P1系统语义 CI

US-11 · 周期性 Lint 找出全局问题，并只修受影响区域

作为用户，我希望系统定期检查跨模块冲突、过期、重复和孤立推断，从而让自治知识状态不会随时间腐化。

验收：Lint 生成问题、证据、严重度、受影响对象和修复候选；修复前后运行回归；低置信修复可隔离但不要求用户逐条处理。

P0用户可逆性工程基线已实现

US-12 · 错误编译后恢复到最近健康状态

作为用户，我希望在一批错误更新污染知识时回滚，从而快速恢复使用，同时保留故障材料供后续修复。

"健康"分两层：systemHealthySnapshot（系统自动：原子发布 + 硬门禁 + 回归通过 + 快照完整）和 userTrustedCheckpoint（用户主动标记满意版本）。候选快照、哈希验证、并发前置条件、写前备份和失败恢复已有工程基线；下一步验收真实长期使用中的 checkpoint 选择、索引一致恢复和维护成本。
Given 当前版本未通过语义回归 When 用户选择最近一个健康版本回滚 Then Wiki、Graph 与索引恢复为同一知识快照 And 新增原始材料仍被保留但其派生结果进入待重编译状态 And v1.1：回滚优先最近的 userTrustedCheckpoint，没有则回 systemHealthySnapshot
P0Agent稳定合同

US-13 · 不同 Agent 通过统一 Context Pack 消费知识

作为通用 Agent，我希望通过稳定 schema 请求任务上下文，从而不用依赖 WGEMemory 的文件结构、具体数据库或编译模型。

验收：Agent 至少可通过 MCP 完成 ingest_material、get_ingest_status、query_context 与 trace_knowledge；请求包含任务、时间、预算、风险偏好和 ScopeContext（principalId + 可选 projectId）；响应包含知识版本、选择理由、证据、冲突、缺口、截断信息与 traceId。MCP、HTTP 和 CLI 必须调用同一 Application Service，payload 语义一致；缺少 ScopeContext 时按 Global-only 处理。
P1系统可恢复失败

US-14 · 编译部分失败时继续提供最后健康知识

作为用户，我希望新材料处理失败不会让整个知识域不可用，从而仍可基于上一健康版本工作。

验收：旧 Canonical 继续服务；失败 run 有明确阶段、输入和重试方式；不得把“仍可使用旧知识”说成“新材料已学会”。
P1产品验证者增益证明

US-15 · 为真实 Benchmark 记录可复现实验

作为产品验证者，我希望每次回答分别记录 Seed、Graph 候选、结构排序、可见门禁、Evidence 闭包、模型、提示、实际 token、工具调用、耗时与知识版本，从而根据过程信号定位增益或退化来自哪一层。

验收：同一 run 的 commit/config/data/prompt/hash 可复现；答案与系统身份分离供盲评；同时报告同预算和自然总成本；失败、超时与被裁剪对象也被记录；首轮结果不可覆盖。
P0AgentGraph 透明路由

US-16 · Graph 帮助找到必要知识，但不把遍历结果倾倒给 Agent

作为通用 Agent，我希望系统用受审计 Graph 找到依赖、冲突和版本路径，同时只给我完成任务真正需要的知识，从而避免 Graph 带来无关上下文和更高总成本。

验收：候选子图与可见子图分离；在线链路必须 Graph-capable，但只有关系意图、版本/影响任务、安全风险或可观测 Seed 覆盖缺口触发时才进入有界 Graph 导航；关系路径满足可见门禁后才展示；RELATED_TO 不得支撑结论；每个可见 Claim 保持条件、provenance 与必要 Evidence 闭包。
P0产品验证者单目标 Loop

US-17 · 每轮只修一个可证伪机制，并在盲域证明泛化

作为产品负责人，我希望系统按 Freeze→Observe→Diagnose→Change→Evaluate→Archive 迭代，从而知道代码变化为什么有效，而不是在同一题集上不断调到高分。

验收：一个 Goal 只有一个主要责任层；先跑 Contract/Micro，再跑 Dev Core，最后才运行冻结 Held-out；看过 Gold 的集合永久转为 Dev；连续两轮无改善停止；领域名、题号、Gold 映射和单材料奖励捷径禁止进入生产逻辑。
P0架构维护者Graph 长期复利历史回归可复用

US-18 · 架构大改后重跑全部历史资产，但不伪装成新盲测

作为架构维护者，我希望在 Graph、Compiler 或 Context Pack 大改后重编历史材料并重跑全部旧题，从而验证迁移、回归、规模和成本，而不丢失过去暴露的失败。

验收：原始 Source 可重新编译；旧 publication、首轮答案和评分只读；新架构使用新 runId、知识快照、配置与处理标签；A/B/C 和已揭示 Held-out 永久为 Dev/Regression；日常只跑 Micro，候选里程碑才跑全量历史回归；泛化结论仍来自新封存 Held-out。
P0产品验证者权限硬隔离

US-19 · Worker、Evaluator 与裁决者不能共享未冻结的答案权

作为产品验证者，我希望写候选算法的 Worker 无法读取 Gold 或覆盖首轮结果，从而让“没有针对答案调参”成为技术事实，而不是 Prompt 承诺。

验收：Reasonix 等 Worker 运行在脱敏任务包和受限 worktree，只能读合同/接口/合成 fixture、只能写白名单文件；Gold、Blind、评分与裁决目录通过 forbid_read 或物理分离不可见。候选代码与结果先冻结 hash，Evaluator 只读候选与 Gold 且不得修改候选，Codex/人工负责最终裁决和不可覆盖归档。
P0架构维护者规模与时间复利

US-20 · Graph 在知识增长和多轮更新中保持局部、准确、可解释

作为架构维护者，我希望在 S50→S200→S1000 与 T0→Tn 中验证路径和影响传播，从而判断 Graph 是否真的减少全库扫描、恢复跨来源依赖并正确更新受影响知识。

验收：S50 用于机制回归，S200 使用真实多领域材料作为第一产品规模门槛，S1000 用真实冻结材料和真实干扰来源做压力测试；不得用无意义生成文本声称质量。分别报告必要路径召回/精度、affected-set recall、unaffected false positive、旧错复发、索引更新范围、读取对象数、p95 延迟和最终固定 Context 预算。

07 / Experience & NFR

体验原则与端到端服务标准

用户不维护

  • 正常路径只有投递、提问、纠正
  • 系统自动完成分类、关系与模块维护
  • 人工界面服务追溯与恢复，不成为必经步骤

状态不说谎

  • 接收、解析、编译、发布必须分开
  • 旧快照可用不等于新材料已吸收
  • 未知、争议与截断明确呈现

失败可恢复

  • 每阶段幂等并可重试
  • 部分失败不影响上一健康版本
  • 回滚后索引与知识快照一致

回答可审计

  • 关键结论到原文最多两次跳转
  • 每个 run 固定知识版本
  • 选择与裁剪过程有记录

建议的服务级目标（MVP 工程目标，不是产品价值结论）

环节目标降级原则
