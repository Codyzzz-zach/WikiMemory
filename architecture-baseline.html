§03 / Status Axes

四个正交状态轴

修 GPT 问题 4：Product Definition 的 epistemicStatus 混合了三种不同问题。新项目拆成三个正交轴 + publicationState。

Axis 1

derivation

"EXTRACTED" | "INFERRED" | "HUMAN_ASSERTED"

结论怎么来的。与可信度正交。

行号：types/index.ts:14

Axis 2

validity

"SUPPORTED" | "DISPUTED" | "UNRESOLVED"

当前是否有争议。独立于 derivation。

行号：types/index.ts:17

Axis 3

lifecycle

"ACTIVE" | "SUPERSEDED"

是否仍然有效（时态）。SUPERSEDED 不删除。

行号：types/index.ts:20

Axis 4

publicationState

"CANDIDATE" | "CANONICAL" | "QUARANTINED"

是否进入默认消费链。Lint 通过自动 Canonical。

行号：types/index.ts:23

正交性验证：一个 Claim 可以同时是 INFERRED + DISPUTED + ACTIVE + CANONICAL。四个轴各自独立变化，不像旧项目 epistemicStatus 那样单选互斥。

四轴组合场景

场景derivationvaliditylifecyclepublicationState
LLM 从原文提取的事实EXTRACTEDSUPPORTEDACTIVECANONICAL
LLM 推导且被另一来源挑战INFERREDDISPUTEDACTIVECANONICAL
被新证据取代的旧结论EXTRACTEDSUPPORTEDSUPERSEDEDCANONICAL
LLM 编译但证据不足INFERREDUNRESOLVEDACTIVEQUARANTINED

Graph 消费规则（graph/index.ts:37-38）：只读 publicationState=CANONICAL && lifecycle=ACTIVE 的对象。

§08 / Parser Layer

Markdown 解析 + blockId 机械生成

修 GPT 问题 7：charStart/charEnd 由 parser 机械生成，不让 LLM 返回。

parseMarkdownFile（markdown.ts:55）→ parseMarkdownContent（markdown.ts:65）：

  1. 分离 frontmatter 和 body（markdown.ts:70-81）
  2. 按 Markdown 结构切块：标题/段落/列表/表格/引用/代码/数学（markdown.ts:124-166, 169-258）
  3. 每个块记录 blockId（fileStem#block-N）+ charStart + charEnd + text（markdown.ts:148-155）
blockId 稳定性：基于文件名 + 块索引生成（如 01-number-systems#block-3）。重新解析同一文件时 blockId 保持一致。LLM 只返回 blockId + exactQuote，程序用 exactQuote 在 block 内做字符串匹配。

TextBlock.kind（markdown.ts:25）："heading" | "paragraph" | "list_item" | "table_row" | "code" | "blockquote" | "math"。

§09 / Ingestor Layer

摄入层：Source + SourceSpan 产出

ingestMarkdownFile（ingestor/index.ts:36）：

  1. 调用 parser 解析 MD（ingestor/index.ts:37-38）
  2. sha256 hash 基于 body 去重（ingestor/index.ts:41-43）
  3. 检查是否已摄入——已存在则读回返回 isDuplicate: true（ingestor/index.ts:46-61）
  4. 从 blocks 生成 SourceSpan——每个 block 一个 span（ingestor/index.ts:76-83）
  5. 写 sources/<id>.json + sources/<id>.spans.jsonl + 追加 manifest.jsonl（ingestor/index.ts:86-109）

mapQuoteToSpan（ingestor/index.ts:125-158）：

  • 输入：所有 SourceSpan + blockId + exactQuote
  • 在 blockId 对应的 span.text 里找 exactQuote 的位置（indexOf）
  • 精确匹配失败时回退到 trim 后再试（ingestor/index.ts:144-152）
  • 返回精确子 span（含精确 charStart/charEnd）；匹配失败返回 null
已验证：5 篇材料测试通过。01-number-systems 产出 103 blocks，mapQuoteToSpan 精确映射成功。

compileSource（compiler/index.ts:52-183）核心流程：

  1. 命题切分（compiler/index.ts:59-69）：LLM 返回 {propositions: [{text, exactQuote, blockId, relatesTo?}]}。用 Zod PropositionResponseSchema 校验。
  2. 映射（compiler/index.ts:72-92）：对每条命题调 mapQuoteToSpan，匹配失败跳过（不信任 LLM 的引用定位）。
  3. 编译（compiler/index.ts:99-183）：LLM 返回 Claim/Concept/Relation draft。构造一等对象时：
    • Claim 的 evidenceSpanIds 需 mapQuoteToSpan 成功（compiler/index.ts:120-127）
    • 没找到 evidence 的 Claim 跳过（compiler/index.ts:131）
    • 所有对象 publicationState=CANDIDATE（compiler/index.ts:141, 172）
    • Relation.source = "intra-material-compile"（compiler/index.ts:176）
Proposition 是中间产物（决策 4A）：PropositionDraft 在 compiler 内部产出，用于 Claim 编译，之后丢弃。不写入 storage，不进 Git。
