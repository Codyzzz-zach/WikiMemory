§02 / v1.2 Changes

v1.2 做了什么——四条轨道

v1.2 由一份审计可信性研究（audit_reliability_research.md）驱动，回答"审计凭什么可信"。按四条并行轨道推进。

轨道 A

审计层改造

prompt 从中性"请审计"改为 L1 对抗型——先假设 Claim 有错，逐句对照原文。5 维度改 binary verdict（pass/fail），删掉 score 0-1（消除评分方差）。加 anchor 字段——审计结论必须溯源到原文，程序验证 anchor 真实存在。

改动文件：prompts/index.ts, types/schemas.ts, linter/index.ts

轨道 B

失败可观测

每次审计记录到 runs/audit-metrics.jsonl：claimId / outcome / 失败维度 / model 快照（pin 版本防 criterion drift）/ 时间戳。这是 meta-eval 的数据源，也是回归基线。

改动文件：linter/index.ts, linter/storage.ts

轨道 C

meta-eval 校准

100 条人工/GPT 标注用例（50 faithful / 50 unfaithful，覆盖 4 类不忠实）。脚本复用真实 semanticCheck 跑全量，算 TPR/TNR/kappa。第一轮 TPR 0.50（anchor 验证 bug），修复后第二轮 TPR/TNR 均 0.98。

新增：scripts/meta-eval.ts, meta-eval-dataset.json

轨道 D

validity 门禁 + 物理隔离

校准达标后推进。compiler 产出 validity=UNRESOLVED；门禁通过才 SUPPORTED。Quarantined 对象物理隔离到 quarantine/ 独立目录，readAllClaims 默认不读它们。

改动文件：compiler/index.ts, linter/index.ts, linter/storage.ts, cli/index.ts

方法论 先校准再改门禁——原因：门禁（UNRESOLVED）的作用是拦下审计判为可疑的 Claim。 如果审计准度未知就拧紧门禁，可能误杀大批正确 Claim 导致系统瘫痪，也可能漏检导致错误流通。 meta-eval 先测出审计的 TPR/TNR，达标后才安全地改默认值。第一轮 TPR 0.50 正是这个决策的价值——发现了 anchor 验证 bug 而非盲目上门禁。
§03 / Audit Calibration

meta-eval 校准结果

"没做 meta-eval 的 judge 不是测量，是 vibe。"——audit_reliability_research.md §1.6

最终结果（第二轮，修复 anchor 验证后）

指标第一轮第二轮门槛含义
TPR0.500 ❌0.980 ✅≥0.8忠实的 Claim 正确放行率（少误杀）
TNR0.980 ✅0.980 ✅≥0.8不忠实的 Claim 正确拦下率（少漏检）
accuracy0.7400.980—总体准确率
Cohen's kappa0.480 ⚠️0.960 ✅≥0.6审计与人工标注的一致性
第一轮 TPR 0.50 的根因 25 个误杀中 23 个是 SEMANTIC_ANCHOR_FABRICATED——不是 LLM 审计能力问题，而是 anchor 验证用精确字符串匹配，LLM 返回的 anchor 做了符号替换（\mathbb{Z}→𝕫）或轻微改写，语义正确但字符串不匹配。 修复为三层容错（精确→归一化→bigram 重叠率）后 TPR 升至 0.98。

审计边界（写进 prompt 头部）

审计只回答封闭问题："这条 Claim 是否忠实于它引用的 SourceSpan？" 审计不回答开放问题："这条 Claim 在世界上是否正确？" 任何维度的判断都必须能用"原文有没有说？"来回答——禁用世界知识判断对错。

5 维 binary verdict（v1.2）

维度封闭问法fail 时的 issueCodefail 严重度
supportSourceSpan 是否明确支持 Claim 每一句？SEMANTIC_SUPPORT_FAILEDerror（硬伤）
additionClaim 是否含 SourceSpan 没有的信息？SEMANTIC_ADDITION_MAJORerror（硬伤）
inference推断是否标为"推断"而非事实？SEMANTIC_INFERENCE_WRONGwarning（软伤）
limits原文条件是否被丢弃或弱化？SEMANTIC_LIMITS_MISSINGwarning（软伤）
citationClaim 是否准确对应引用的 span？SEMANTIC_CITATION_FAILEDerror（硬伤）

硬伤维度（support/addition/citation）fail → QUARANTINE；软伤维度（inference/limits）fail → CANONICAL 但需修正。anchor 编造 → SEMANTIC_ANCHOR_FABRICATED → QUARANTINE（审计结论本身不可信）。

L1 的已知边界 L1（同模型 + 对抗 prompt）只能减少"误杀正确 Claim"（EIR），无法显著提升"发现错误 Claim"（ECR）。 当前 TNR 0.98 在数学语料上表现好，但这是 L1 的天花板区域。 Phase 2 Benchmark 时应做 L2（换模型审计）敏感性实验，确认跨模型是否进一步提升。

v1.2 validity 语义修订
  • UNRESOLVED（待证明）：新 Claim 的初始状态。证据不足、尚未通过门禁。可导航但不进推理链。
  • SUPPORTED（已支持）：门禁通过——审计证明 Claim 忠实于 SourceSpan。
  • DISPUTED（有争议）：只由真实的可比较冲突产生（CONTRADICTS 边），不再由 support=warning 等价产生。
删除了 v1.1 的 support=warning → DISPUTED 直接映射——证据弱不等于存在反证。

§09 / Compiler

编译层（v1.2: validity 初始改 UNRESOLVED）

compileSource()（compiler:52-183）三步：命题切分（LLM 返回 blockId+exactQuote）→ mapQuoteToSpan 映射 → Claim/Concept/Relation 编译。

v1.2 关键改动 所有产出 publicationState=CANDIDATE（不变），但 validity 从 SUPPORTED 改为 UNRESOLVED（compiler:138, compiler:172）。 依据：不假定编译结果可信——新 Claim 是"待证明"的，只有门禁通过才升级 SUPPORTED。

Proposition 是中间产物，不持久化（决策 4A）。

§10 / Graph

Graph 层

buildGraph：从 Canonical Claim/Relation 构建。过滤 publicationState=CANONICAL && lifecycle=ACTIVE。v1.2 起这些对象来自主目录（claims/claims.jsonl），Quarantined 在物理隔离区不参与构建。

walkGraph：BFS 从种子扩展，返回 { claims, relations, disputedClaims, unresolvedClaims }。方向检查 + 消费矩阵分类。

searchClaims：关键词匹配，过滤 allowRetrieval——UNRESOLVED 和 DISPUTED 可搜到，CANDIDATE/QUARANTINED/SUPERSEDED 被排除。

§11 / Context Pack

Context Pack（Map-first）

buildContextPack() 10 步流程：加载状态 → buildKnowledgeMap（检索前地图）→ buildGraph → selectSeeds（map+keyword 双路）→ walkGraph（排除 RELATED_TO）→ 预算控制 → 回填证据 → conflictsAndConditions（从 disputedClaims）→ knownGaps（从 unresolvedClaims）→ 裁剪 taskMap。

wikiModules 为空——Phase 2 实现。预算 4chars≈1token 在中文/公式上有低估风险（Review 断点 7），Gate 2 前需修。
