§04 / Loader & Ingest

当前只摄入 Markdown，但格式能力已经解耦

DocumentLoader 只负责把外部格式机械转换为统一的 LoadedDocument：uri、sourceType、loaderVersion、sourceKey、parsedText 和可回溯 blocks。Loader 不得生成 Claim，也不得做语义判断。

DocumentLoader.canLoad(filePath) DocumentLoader.load(filePath) → LoadedDocument LoaderRegistry.resolve(filePath) → 唯一匹配的 adapter ingestLoadedDocument(...) → Source + SourceSpan[]
  • 默认 registry 目前只注册 MarkdownLoader；PDF/HTML 未伪装成“已支持”。
  • 第三方 Loader 可注册到同一 registry；测试已用 fake PDF loader 验证适配边界。
  • Ingestor 对每个 block 验证 offset、范围和 parsedText.slice(start,end)===text，防止不可回溯 Loader 产物进入系统。
  • readings/back-to-basics/latex/ 中已确认存在多文件 TeX、样式、参考文献和图片，但按当前产品决策不摄入；未来 TeX adapter 必须在 Loader 边界实现 include/bibliography/asset 解析，不能把 TeX 逻辑塞进编译器。
  • Source 以正文 hash 建立不可变证据载体；同 Source 重跑不会删除原文或 Span。

§06 / Contracts

对象、状态轴与 provenance 语义

四个正交状态轴

轴枚举回答的问题
derivationEXTRACTED / INFERRED / HUMAN_ASSERTED结论怎么来的？
validitySUPPORTED / DISPUTED / UNRESOLVED当前是否被支持或存在争议？
lifecycleACTIVE / SUPERSEDED是否仍是当前知识？
publicationStateCANDIDATE / CANONICAL / QUARANTINED是否进入默认消费边界？

Claim 证据角色不是两个重复字段

provenanceRefs

谁在何时提出

回答出处和血缘，不自动证明内容成立。SourceSpan、AssertedRecord、ExperimentRecord 都可以作为 provenance。

supportingEvidenceRefs

凭什么可以支持

回答该 Claim 为什么能进入 SUPPORTED。其合法类型由 claimKind 决定。

claimKind允许的支持依据硬规则
FACTSourceSpan 或 ExperimentRecordAssertedRecord 只能在 provenance；用户说过不等于事实已证明
DECISION同 Claim、同 PROJECT scope 的有效 AssertedRecord必须有 assertedBy/assertedAt/authorityBasis/assertionText
PREFERENCE同 Claim、同 PERSONAL scope 的有效 AssertedRecordassertedBy 必须是该 PERSONAL 主体

材料型 FACT 中，同一个 SourceSpan 同时是“原话出自哪里”和“原文是否支持 Claim”，因此两组引用相同可以是正确语义，不应仅凭数组相等判定设计失效。

Claim 忠实度门禁

只回答 Claim 是否忠实于引用原文，不判断世界事实。维度为 support、addition、inference、limits、citation；固定 JSON schema、证据下标和 failedDimensions 一致性由程序验证。基础设施故障或连续非法 verdict 会让运行失败，不会伪装成“Claim 不忠实”。

Relation 边级门禁

端点分别正确不等于边正确。Relation 独立审计 relation、type、direction、conditions 四维；通过后只保留审计器明确选择的边级证据。v1.2 进一步要求被选择的证据必须同时覆盖 FROM 与 TO，拒绝用单侧引文和模型外部知识补全另一端。真实 E2E 仍发现模型把“欧拉公式成立”误判为支持“可由 Taylor 展开推出”，证明协议正确不等于模型每次执行正确；该边已由人工否决入口隔离。

由于真实人工抽检中的 EQUIVALENT_UNDER 为 4/4 假阳性，该类型现由结构门禁统一标记 RELATION_EQUIVALENCE_REVIEW_REQUIRED 并进入 quarantine；在独立人工复核或校准 critic 完成前，不能自动晋级。

  • EQUIVALENT_UNDER 必须有非空 conditions，且两端在相同对象域与范围内具有相同真值条件；一般定义与具体直觉、共享术语、循环条件均不能制造等价。
  • conditionStatus 区分 PRESERVED、EXPLICIT_NONE、UNVERIFIED，避免空数组同时表示“确实无条件”和“没提取到”。
  • 跳过语义审计时，Relation 只能保持 UNRESOLVED/UNVERIFIED，不能冒充 SUPPORTED。
  • Graph 只接受当前审计版本，旧边自动降级；审计规则升级不会静默沿用历史边。

召回边界

  • 只比较“新 Source Claim”与召回的旧 Claim，不做全库 O(n²) 两两检测。
  • 召回使用 Concept 名称/别名和文本 bigram 相似度；当前上限 40 个候选，不依赖 embedding。
  • Concept ID 不再包含 Source hash；同名、同领域且 boundary 兼容时复用既有 ID；同名不同边界会分叉。
  • 跨材料 Relation 的 telemetry 使用独立 CROSS_MATERIAL_RELATION_DETECTION 阶段。
  • Source 重编导致旧 Claim ID 消失时，不再只依赖 Graph 读时过滤：发布层会把其他 Source 拥有、但指向旧 Claim 的 cross 边连同 BROKEN_RELATION_ENDPOINT 原因先写入 quarantine，再移出 canonical。
  • Claim 去重当前只覆盖规范化 statement+conditions 的确定性重复；跨来源语义改写/同义 Claim 尚不会自动合并。
当前验证边界 01→02→03 已真实执行。最终 backfill 每篇均报告 40 个召回候选；机器门禁通过 4 条，人工抽检否决 1 条错误 SUPPORTS，保留 3 条 Cauchy/完备性 RELATED_TO。可以宣称正边生成、拒绝和消费链路通过；不能宣称自动审计已达到无需人工抽检的生产精度。

§10 / Read Contract

Graph 与 Context Pack 的双重消费保护

Graph 可见性

buildGraph() 只接受 Canonical+Active Claim，并进一步要求 Relation：非 UNRESOLVED、conditionStatus 已确认、relationAuditVersion 等于当前版本、from/to 端点仍存在。双向 adjacency 仅用于导航，不改变关系方向语义。

RELATED_TO 已进入 Context Pack 的图遍历白名单，用于跨材料发现邻居；其类型语义固定为 canSupportConclusion=false，因此 Agent 可以看到“这两条知识相关”，但不能把弱相关当成证明或推导。

v1.6 Seed 边界：原实现按空格切查询，会把整句中文当成一个 token。现在 Seed Retriever 独立于 Graph，使用 Unicode 词、中文二元/三元片段、英文字符片段和 IDF 评分，并把 Claim 的精确 EvidenceSpan 文本纳入索引；L²、L^2 等排版差异做最小标识规范化。查询含未覆盖专名时，不允许只凭“不同/条件/什么”等普通片段启动 Graph。Graph 只能扩展可靠 Seed，不能制造 Seed。

该规则用数学、软件迁移、对比学习和产品发布四个独立领域的合成语料验证；生产代码中没有题号、材料名、数学关键词表或 Gold 映射。SelectionLog 明确记录 queryFeatures、eligibleClaims、matchedClaims 和 evidenceIndex，空 Seed 会区分“库未覆盖”和“原文未编译为 Canonical Claim”。

Claim 状态可检索可支撑推理Context Pack 区域
CANONICAL + ACTIVE + SUPPORTED是是正文
CANONICAL + ACTIVE + DISPUTED是否conflictsAndConditions
CANONICAL + ACTIVE + UNRESOLVED是否knownGaps
SUPERSEDED / CANDIDATE / QUARANTINED否否排除

Scope 隔离

  • 无 ScopeContext：只允许 GLOBAL，禁止默认全选。
  • 有 principalId：GLOBAL + 该主体 PERSONAL。
  • 有 projectId：再叠加该 PROJECT；其他个人和项目不可通过 Relation 泄漏。

预算与证据闭包

Context Pack 先做 Map→Seed→Subgraph→Evidence，再以混合中英文 token 估算器对最终 JSON 序列化载荷复核。裁剪时保持 Relation→Endpoint、WikiModule→Claim、Claim→Evidence 闭包；预算过小到无法容纳最小合同外壳时显式报错，不返回悄悄超预算的 Pack。
