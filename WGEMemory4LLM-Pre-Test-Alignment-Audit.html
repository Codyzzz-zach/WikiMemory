01 / Executive Verdict

当前架构是合格的 Phase 0+1 技术薄切片，但不是可代表产品定义的测试对象

Source、SourceSpan、Claim、运行时 Schema、Claim Lint、基础存储与 Context Pack 外壳已经形成了合理地基；但产品价值依赖的 Wiki 语义、跨材料关系、Concept 对齐、纠正传播、原子知识版本和真正的 map-first 选择尚未闭环。因此现在直接运行 A–E 主实验，得到的不是“WGEMemory4LLM 是否有用”，而是“一个 Claim + 关键词 + 薄 Graph 原型表现如何”。

STOP

暂缓产品级 Benchmark

C、D、E 三组的定义条件尚不成立；跨文档和进化题测不到产品承诺。此时的低分不可归因于产品假设，高分也可能来自回答模型或题目关键词。

GO

立即开始契约与组件测试

解析、去重、证据定位、Schema 拒绝、Claim 门禁、Quarantine 隔离和状态过滤都适合现在测试；这些测试还能尽早暴露状态断点。

最高风险：Architecture Baseline 描述 Relation 由 Compiler 产出为 CANDIDATE，随后只有 lintClaims 完成晋级，Relation 被直接保存；Graph 又只消费 CANONICAL + ACTIVE。按文档信息推导，Relation 缺少从 Candidate 到 Canonical 的发布路径，Graph 可能在结构上存在、在运行时却没有可消费边。必须用契约测试先证伪或修正这一点。
02 / Product Invariants

任何架构都必须服务同一条因果链

flowchart TD G["目标：Agent 随使用持续改善"] --> B["后续任务行为改变"] B --> C1["少重复解释"] B --> C2["少复发已纠正错误"] B --> C3["跨材料判断更完整且有依据"] E["Evidence：可信锚点"] --> K["可修正知识状态"] W["Wiki：完整语义"] --> K R["Typed Graph：拓扑与依赖"] --> K K --> P["任务化 Context Pack"] P --> B B --> F["新证据、纠正与任务结果"] F --> K

这条链中任何环节缺失，产品都不能用其它产物数量补偿：没有 Wiki，Agent 得到的是碎片；没有跨材料关系，Graph 不能恢复知识网络；没有版本与影响传播，系统只是追加知识；没有后续行为变化，Git commit、节点数与页面数都不构成价值。

不可被替换的层产品责任不能用什么伪装完成
Evidence让 Claim、Relation、Wiki 回到原文与来源时态“LLM 判断可信”、相似文本或漂亮引用格式
Wiki提供围绕稳定问题的完整语义与当前认识Claim 列表、每篇文章一份摘要
Typed Graph保存关系、条件、方向、冲突与影响依赖双向链接、关键词共现、无限 BFS
Compiler + Lint让新证据成为受门禁约束的知识状态 diff只生成新文件、只检查 JSON 格式
Context Pack把当前知识投影为任务相关、预算可控、风险显式的输入把全部 Wiki 塞进上下文、检索后再补一个“地图摘要”
Evolution让纠正沿依赖改变后续行为，同时保留旧证据全库重写、删除旧结论、只在当前对话记住纠正

04 / Logical Contradictions

必须先处理的七个逻辑断点

1. Relation 没有被证明能进入 Canonical Graph

flowchart LR C["Compiler 产出 Relation"] --> X["CANDIDATE"] X -. "文档未描述 Relation Lint / 晋级" .-> K["CANONICAL"] X --> S["直接 appendRelations"] K --> G["Graph 只消费 Canonical + Active"] S -. "若仍是 Candidate" .-> Z["Graph 无可消费边"]

修正原则：Claim 与 Relation 必须作为同一候选 diff 受审。Relation 的端点、类型兼容、方向策略、条件、Evidence、状态和端点发布状态都通过后，才能与 Claim 一起原子发布；任何端点被隔离，依赖它的 Relation 也不能进入默认图。

2. Graph 的“双向邻接”与关系方向语义没有分层

为检索建立双向邻接是合理的，但“可从两边找到”不等于“可从两边推理”。A REQUIRES B 允许从 B 反向找到依赖者 A，却不能被解释成 B REQUIRES A。Graph 输出必须同时保留原始方向和本次遍历方向，并为每种 RelationType 定义：是否对称、是否允许反向导航、是否允许作为答案推理依据。

关系示例正向推理反向导航反向推理
REQUIRES / DERIVED_FROM / SUPERSEDES允许，需条件与证据允许，用于找依赖者或历史禁止
SUPPORTS允许表达支持允许找支持来源不能自动变成“被支持者支持来源”
CONTRADICTS / EQUIVALENT_UNDER通常对称，但条件必须保留允许按类型语义允许
RELATED_TO不能支撑结论仅允许扩展候选检索禁止

3. taskMap 当前是结果摘要，不是 map-first 的选择机制

当前流程

关键词种子 → Graph 扩展 → 预算裁剪 → Evidence → 生成 taskMap

地图只能解释“已经选了什么”，不能帮助系统在全局主题、争议、最近变化中决定“应该选什么”。

定义要求

任务意图 → 全局导航地图 → 候选模块/概念 → 有类型子图 → Evidence → Pack

地图是低成本导航索引，参与种子生成与召回诊断，而不是回答后的装饰。

4. 定义文档的“两状态轴”已经落后于架构语义

Product Definition 把 ASSERTED / INFERRED / DISPUTED / SUPERSEDED 放进单一 epistemicStatus；当前架构正确地拆成 derivation、validity、lifecycle、publicationState 四轴。应以四轴为新合同，并同步所有 Relation schema、状态图、User Story 和 Benchmark 术语。否则测试报告会把“怎么来的、是否有争议、是否仍有效、是否发布”再次混成一项。

derivation: EXTRACTED | INFERRED | HUMAN_ASSERTED validity: SUPPORTED | DISPUTED | UNRESOLVED lifecycle: ACTIVE | SUPERSEDED publicationState: CANDIDATE | CANONICAL | QUARANTINED

四轴不应机械套在所有对象上：Claim 与 Relation 使用完整四轴；Concept 至少需要发布/生命周期与 merge 状态；WikiModule 是派生视图，需要发布/生命周期和版本；Source/SourceSpan 则以不可变来源状态为主。

5. Canonical 被当成“能否看见”，却还没有定义“能否支撑推理”

Canonical 不等于真理，这个方向正确；但 Graph 目前只按 Canonical + Active 过滤，可能把 UNRESOLVED 当作普通边或 Claim 使用。需要冻结消费矩阵：

组合检索/展示可否独立支撑结论Pack 行为
CANONICAL + ACTIVE + SUPPORTED默认允许允许，仍需 Evidence正常使用
CANONICAL + ACTIVE + DISPUTED必须允许不能作为无争议单一结论强制进入 conflictsAndConditions
CANONICAL + ACTIVE + UNRESOLVED可用于导航和缺口禁止进入 knownGaps，不进入必要推理链
CANONICAL + SUPERSEDED仅历史/asOf 查询当前任务禁止显式时间请求时使用
CANDIDATE / QUARANTINED诊断路径可见禁止默认链完全隔离

6. 原子发布与稳定身份缺失，使“进化”无法被可靠描述

同一批材料可能同时修改 Claim、Relation、Concept、Wiki 和索引。分别追加会产生中间不一致状态；没有稳定逻辑身份，重新编译也无法区分“同一 Claim 的新版本”“新 Claim”“旧 Claim 被取代”。测试前至少需要：

  • 候选快照：一次 run 的全部派生物和删除/取代意图；
  • 稳定逻辑 ID + 不可变版本 ID；
  • 整体 Lint 与回归后一次性发布；
  • knowledgeVersion 指向同一批 Claim/Relation/Wiki/索引；
  • 失败时继续服务 lastHealthy，而不是部分新、部分旧。

7. “warning 即 Canonical”过于依赖未类型化语义

Architecture Baseline 使用“issues 文本包含‘冲突’”决定 DISPUTED，其它 warning 自动 Canonical。条件遗漏、证据不足、错误引用都可能被模型以不同措辞表达，不能依赖字符串命中。Lint issue 必须有稳定 issueCode、severity、affectedObject 与 recommendedState；只有允许发布的 minor warning 才能自动晋级。

05 / Benchmark Alignment

现有 Benchmark 的科学方向正确，但决策树把“产品价值”错误绑定在 E 组

Product Definition 已明确：Typed Graph 是否进入在线问答主链由 E vs C 决定；即使在线无增益，Graph 仍可服务 Lint、依赖与增量重编译。因此产品价值不能只定义成 E vs B。若 C 明显优于 B、E 因 Graph 噪声低于 C，产品的 Wiki + Evidence + Compiler 价值依然成立，正确结论应是“保留产品、Graph 在线降级”，而不是直接回退文件夹。

Benchmark v1.1 必须增加的修正

  1. 把当前 80 题分层：公开 Dev/Pilot 与最终评估分开。当前题目已完整写入文档并参与架构设计，不应再全部称为 held-out；主报告必须单独报告未用于调参的隐藏子集。
  2. Pilot 不与主结果混算：用于定预算和工具上限的 20 题单独报告；剩余题或新增隐藏题承担确认性结论。
  3. 产品门禁改为 C vs B，再由 E vs C 决定 Graph 在线角色：最终再用“被选中的 WGE 方案”与 B 做产品结论。
  4. 增加 Wiki 指标：证据忠实度、长期问题覆盖、冲突保留、模块边界一致性、新材料更新旧模块比例；否则 C vs B 的成因无法解释。
  5. 加入编译漏失观测：命题数量、quote 映射失败率、被跳过对象及原因、Claim/Relation 各状态数量。任何跳过不得静默。
  6. 严格 token 预算：最终 Pack 应用模型 tokenizer 或 API usage 做硬校验，Evidence、冲突和选择日志都计入预算；超出时按预注册优先级裁剪并记录。
  7. 每组使用同一知识快照：C/D/E 应由同一编译产物通过运行时开关消融，不能各自重新编译出不同 Wiki。
  8. 真实 30 天试验比较 B 与“实验选出的 WGE 运行时”：不能预先固定 E。
06 / Test Entry Gates

把“测试”拆成五道门，不再用一次大实验掩盖缺口

flowchart TD G0["Gate 0：语义合同冻结"] --> G1["Gate 1：组件与隔离测试"] G1 --> G2["Gate 2：5 篇最小产品切片"] G2 --> G3["Gate 3：20 篇 A–E 静态实验"] G3 --> G4["Gate 4：T0–T4 进化实验"] G4 --> G5["Gate 5：30 天真实 AI 学习"]

Gate 0 · 语义合同冻结

  • 四状态轴写回 Product Definition，所有文档不再出现旧联合轴；
  • 冻结 Claim/Relation 的消费矩阵与 Lint issueCode；
  • 冻结 RelationType 的方向、对称性、导航与推理资格；
  • 确认用户纠正的权威边界；
  • 定义稳定逻辑 ID、版本 ID、knowledgeVersion 与原子发布边界。

Gate 1 · 当前即可开始的组件测试

测试必须证明失败时说明
Parser / SourceSpan字符位置、中文、Markdown、表格、公式、重复句与换行保持可定位Evidence 地基不可信，后续全部停止
Hash 幂等同内容不同文件名不重复；失败 run 可明确重新编译知识会重复或无法恢复
LLM Schema坏 JSON、坏枚举、坏引用被拒绝且有诊断类型只存在于编译期
Claim Lint无证据、条件遗漏、证据不支持被正确分流Canonical 会放大错误
Relation 晋级至少一条合格边进入 Canonical；坏边进入 Quarantine；依赖坏端点的边不进图Graph 只是空壳或污染源
隔离路径Quarantine 在搜索评分、Graph 扩展和 Pack 组装之前即被排除“晚过滤”仍会污染选择

Gate 2 · 5 篇最小产品切片

不要直接冲 20 篇。先用 5 篇构造一个必须同时出现以下对象的可否证闭环：

  • 至少 2 个按长期问题组织、会被新材料更新的 WikiModule；
  • 至少 1 个跨来源 Concept 合并案例与 1 个同名异义分叉案例；
  • 至少 3 条跨材料关系，其中含一条有条件边、一条冲突边；
  • Context Pack 真正按 Map → Subgraph → Wiki → Evidence 选择；
  • B/C/E 可由同一资产和同一回答壳切换；
  • 12–20 道 Dev 题包含单跳、多跳、条件、无答案与一次用户纠正；
  • 所有 run 保存实际输入、被丢弃项、知识版本、模型与 prompt hash。
Gate 2 的目的不是宣布产品成功，而是确认测试对象已经具有产品定义的最小形状。若 C 仍不能超过 B，或 E 只增加噪声，就应在扩到 20 篇前调整假设。

Gate 3–5 · 只有前一门通过才进入

  • Gate 3：20 篇静态 A–E；冻结确认性题集与运行配置，输出盲评和错误归因。
  • Gate 4：T0–T4 纠正、影响传播、局部重编译、lastHealthy、回归与过度重编译。
  • Gate 5：30 天真实 AI 行业与技术学习，验证重复解释、查证成本、跨文章遗漏和纠正复发。

08 / Decisions to Align

只剩两个需要产品层确认的问题

其它阻断项都可以直接从既有目标推出，不需要你选择字段名或技术实现。下面两项会真实改变用户体验和系统权力边界，需要明确冻结。

决策 A · 用户纠正是否等于事实证据？

推荐：双通道权威。

  • 事实性纠正：保存为 HUMAN_ASSERTED；立即让旧结论进入 DISPUTED 或停止无条件输出，但新断言在获得来源前保持 UNRESOLVED，不能独立成为事实依据。
  • 个人偏好、项目决策、本人任务结果：用户是第一权威，可作为 SUPPORTED 的个人域 Evidence；仍保留时间、范围与来源类型。

这比“用户说什么都是真理”更安全，也比“用户纠正只触发搜索、长期状态不变”更符合产品目标。

决策 B · taskMap 是检索前地图，还是检索后摘要？

推荐：检索前地图，作为 P0。

它必须用低成本方式提供候选主题、稳定问题、已知争议、最近变化与关键概念，参与 Wiki/Graph 的种子选择；Context Pack 最终仍可携带裁剪后的 taskMap。如果只做检索后摘要，应改名 selectionSummary，并删除“先地图后子图”的产品承诺。

建议冻结结论：选择“决策 A 双通道权威 + 决策 B 检索前地图”。在确认前，可以运行 Gate 1 组件测试；不应冻结 Product Definition v1.1，也不应进入 Gate 2 之后的实验。
09 / Final Alignment Statement

测试前的统一口径

WGEMemory4LLM 不是 Claim 抽取器、Graph RAG 或自动 Wiki 中任意一个单点。它要证明的是：系统能把新材料和纠正编译为可追溯、可版本化、可局部修正的知识状态，并通过任务化 Context Pack 改善同一个 Agent 的后续行为。测试必须先确认对象、状态和信息流使这种行为“有可能发生”，再比较它是否真的比文件夹搜索更好。
