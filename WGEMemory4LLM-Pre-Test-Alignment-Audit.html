01 / Executive Verdict

工程地基已建立；现在必须从“安全编译”转向“保真、组织与长期效用”

旧版 v0.9 判断 Relation 发布、原子快照、跨材料扫描和演化链路尚未闭环；这些结论已经过期。当前系统已经具备不可变证据、有界编译、Claim/Relation 双门禁、物理隔离、两阶段原子发布、知识快照、跨材料扫描和受审批的纠正/冲突事务。新的主要矛盾不再是“能否安全写入”，而是“严格投影是否损失了太多真实语义，以及这些结构是否真的让 Agent 长期变好”。

KEEP

保留安全知识状态内核

Evidence、Canonical/Quarantine、四状态轴、双门禁、原子发布、版本和回滚是错误复利场景下的必要基础，不能因为小规模原文检索暂时领先就拆掉。

SHIFT

停止继续围绕通过率优化

接下来优先衡量信息漏失、Quarantine 假阴性、关系召回和 WikiModule 效果；现有五篇与 24 篇数据降级为 Dev/Regression，不再承担泛化结论。

当前最危险的自我欺骗：把“原文仍在磁盘”当成“Agent 没有损失知识”，或把“错误边被隔离”当成“Graph 已经高质量”。原始证据可恢复只证明没有不可逆删除；默认消费投影是否保留了任务所需事实、条件、语境和关系，必须另行测量。
02 / First Principles

知识编译不是提取比赛，而是一个受约束的有损变换

完整但昂贵"] --> C["编译变换 f(S)"] C --> K["长期知识状态 K

任何压缩都会丢信息。问题不是“能否零损失”，而是：是否丢掉了对未来任务重要的信息；是否引入了原文没有的内容；丢失后能否发现并回退到原文；新证据进入后是否能局部修正而不污染无关知识。

真实性每个可消费断言和强关系都有可解析来源错误引用率、无证据发布率、审计精度节点数量、模型置信度
语义保留事实、条件、例外、指代、表格和推导链不被原子化破坏Source→Claim 召回、条件保真、Quarantine 假阴性eligible block 100% 命中

可恢复失败不破坏 last healthy；能回到原文和历史状态原子性、回滚、悬空引用、恢复时间“文件还在”
架构判断原则：安全门禁有第一性原理依据；具体 Relation 类型、检索算法、Wiki 结构和 Board 模式没有天然正确性，必须通过消融与 Held-out 结果赢得存在权。
03 / LiteWikiagent Heritage

LiteWikiagent 是经验库，不是要复制的旧架构

旧项目真实解决过“如何让 Agent 阅读和探索知识”的问题，也真实暴露了“生成式 Wiki 如何把推断伪装成知识”的问题。后续施工必须同时继承它的产品洞察和吸收它的工程教训。

应继承

面向 Agent 的语义组织

  • 围绕问题与概念组织可读模块；
  • 显式表达 Interpretation、Use For、Limits；
  • concept/method/case/question/insight/counter 等不同知识角色；
  • ask/trace/expand/compare/challenge/inspire 等任务视图；
  • 文件、图和向量的混合检索经验；
  • Loader、daemon 和持续摄入的产品体验。
必须拒绝

写入先于可信边界

  • 无证据时回退到虚假的固定引用；
  • 生成 Interpretation 后再尝试审计；
  • 审计异常静默、文件仍已写入；
  • 旧节点先删除、新快照未原子完成；
  • 关系只凭同主题或模型置信度发布；
  • 把人类可读页面直接当作知识权威。
应重建

在 Canonical 之上的 Wiki

  • WikiModule 只能引用 Canonical Claim；
  • 解释文本中的每个断言可追溯 Claim；
  • 稳定地址与内容版本分离；
  • Claim 失效时模块自动失效或重建；
  • Board 模式成为同一知识状态的运行时视图；
  • 探索性推断必须与来源事实分层展示。
旧经验当前系统下一代正确组合
Wiki 页面连贯、适合阅读，但容易把推断写成事实Claim 可审计，但阅读时碎片化Canonical Claim 是权威；WikiModule 是可重建的语义视图
六种 Board 提供丰富任务脚手架单一 Context Pack 更简单可控先冻结统一 Pack 合同，再把 Board 作为可消融的选择策略
混合检索召回强，但失败可静默降级词法 Seed 可解释，但召回仍有限统一候选日志下比较 lexical/BM25/vector/graph，不把任一路写死
PDF/TeX 与 watcher 体验较完整只实现 Markdown，Loader 已解耦产品价值成立后复用旧 Loader 经验接入，不把格式逻辑塞进 Compiler
历史经验使用规则：旧项目可以提供需求、反例、测试案例和实现思路；不能直接复制其未经当前证据合同验证的节点、关系、审计分数或发布逻辑。

07 / Confirmed Next Work

接下来正式做三件事，按依赖顺序推进

工作包 A · 建立信息守恒审计

目的：知道编译到底丢了什么，而不是只知道多少对象通过门禁。

  1. 从数学、软件/平台、产品政策、研究记录中各选真实材料，人工标注事实、条件、跨句指代、表格、公式/代码和关系；现有五篇只保留为 Dev。
  2. 建立 Source fact → Proposition → Claim → Canonical/Quarantine → Retrieval 全链路账本。
  3. 把证据合同从“单个最小 exactQuote”扩展为“主引用 + 必要上下文”，上下文必须仍有精确 Span，不允许自由补写。
  4. 分层抽检 Claim 和 Relation Quarantine，统计 false negative；不能再只统计通过率。
  5. 分别报告正文、表格、公式、代码、标题限定和跨句因果的表现。
建议首轮规模：4 个领域 × 5 篇文档；每域人工冻结 40 个事实单元、15 条关系和 10 个条件/语境案例。规模不追求大，先让召回指标可信。

工作包 B · 自动 WikiModule 最小闭环

目的：恢复 LiteWikiagent 的语义组织优势，同时不恢复其“解释即权威”的风险。

  1. 从稳定问题或高价值 Concept 生成模块候选，不按“一篇文章一个摘要”生成。
  2. 模块包含 coreQuestion、currentUnderstanding、conditions、disputes、claimRefs、conceptRefs、dependencies 和内容版本。
  3. 模块正文每个陈述必须能映射到一个或多个 Canonical Claim；模型综合必须显式标记为 synthesis。
  4. Claim 进入 SUPERSEDED/DISPUTED/QUARANTINED 后，依赖模块自动失效；事务完成后局部重建。
  5. 同一稳定地址在 T0→T3 中持续更新，而不是不断创建新页面。
  6. 建立 Wiki 忠实度、覆盖、边界一致性和更新正确性门禁。

工作包 C · 构建独立产品实验

目的：第一次产生不被当前开发过程污染的产品证据。

  1. 把五篇数学、16 题和 24 篇演化集锁定为 Dev/Regression，禁止继续作为主结论。
  2. 由产品方或独立生成方准备 Held-out；施工方只获得 schema 和训练示例，不获得题目与 Gold。
  3. 同一知识快照派生四组：原文检索 B、Claim-only P0、Wiki-only W、Wiki+Typed Graph E。
  4. 在 1.5k / 3k / 6k / 12k 实际上下文 token 档位比较质量、hard failure、延迟和成本。
  5. 回答 Judge 与编译模型分离；至少 20% 分层样本由人类复核。
  6. 实验前预注册死亡标准；看完 Held-out 后修改系统，该集合立即转为 Dev。

09 / Definition of Usable

产品到什么程度才可以称为“可用”

“可用”不是一个布尔词。必须区分工程可用、受控 Pilot 可用和真实产品可用。当前系统处于 L1 与 L2 之间：安全内核可用，但 Agent 产品尚不可用。

级别定义硬门槛当前状态
L1 · 工程内核可用开发者可以安全摄入、编译、隔离、发布、查询和回滚悬空引用=0；失败保留 last healthy；状态和 run 可审计；默认消费 fail-closed基本达到
L2 · 受控知识库可用在多个领域中，系统能保留事实与条件，并生成可更新 Wiki独立 Gold 上 Claim precision ≥95%、事实 recall ≥90%、条件保真 ≥90%；强 Relation precision ≥90%、recall ≥70%；Quarantine 假阴性有界；Wiki 更新回归通过未达到
L3 · Agent Pilot 可用在相同实际 token 和独立 Held-out 上，编译知识提供可重复的质量或成本优势质量不劣于强文件检索超过 2%；hard failure 不增加；在不降质时上下文成本下降 ≥40%，或同成本回答质量显著提升；纠正后复发率 ≤5%未达到
L4 · 产品可用真实用户/Agent 在持续使用中明显变得更省解释、更少复发、更完整至少 30 天、5+领域、100+真实任务、2+纠正周期；重复解释下降 ≥30%；旧错复发 ≤5%；跨材料完整性优于基线；可恢复且维护成本可接受尚未验证
这些阈值是 v2.0 的产品验收基线。它们可以在首次预注册前基于成本和样本量调整；一旦 Held-out 开始运行，不能根据结果下调门槛。L2 是内部知识库可试用线，L3 是小范围 Agent Pilot 线，只有 L4 才能对外称“持续自进化知识产品可用”。

立即停止或收缩的条件

  • WikiModule 完成后仍无法在同预算下接近强文件检索，且没有显著 token/延迟收益；
  • 严格门禁导致事实或关系 recall 长期低于门槛，必须靠人工逐条补救；
  • 纠正后旧错误仍复发，或无关知识随着演化持续退化；
  • Graph 在 Held-out 中不增益且持续引入 hard failure——此时 Graph 退回离线影响分析，不进入在线回答主链；
  • 文件夹 + Agent 在相同预算和长期任务上稳定达到同等效果——此时产品应收缩为轻量文件组织或 Agent Skill。
10 / Final Alignment Statement

后续施工与审查的统一口径

WGEMemory4LLM 的最终产品不是一个更严格的 Claim 抽取器。它应当把原始材料安全地编译为可演化知识状态，再把这些碎片组织成稳定、可读、可更新的 Wiki 语义，并在任务时以更低成本改善同一个 Agent 的后续行为。Evidence 决定它可信，Wiki 决定它可理解，Graph 决定它可传播，Evolution 决定它会成长，真实长期结果决定它是否值得存在。
  1. 从 LiteWikiagent 学产品表达，不能继承其 fail-open 权威模型。
  2. 当前安全内核继续保留，但新的优化目标改为语义召回、Wiki 更新和 Agent 长期效用。
  3. 现有测试集只做回归；主结论必须来自独立 Held-out 与真实长期使用。
  4. 下一施工顺序固定为：信息守恒审计 → 自动 WikiModule → 同资产消融 → Held-out → 30 天真实 Pilot。
  5. 达到 L3 才允许小范围试用，达到 L4 才能称为产品可用。
